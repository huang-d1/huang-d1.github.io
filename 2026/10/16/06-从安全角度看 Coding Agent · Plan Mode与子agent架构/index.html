子Agent架构

这里的子agent架构执行流程大体上跟我们之前实现的executeSkill fork类似

一些区分

executeSkill fork 是什么

它表示：

执行某个 Skill 时
→ 不让主 Agent 直接执行
→ 新建一个 Agent 实例
→ 把 Skill 内容作为它的系统提示词
→ 给它一组受限工具
→ 子 Agent 独立完成任务
→ 返回最终文本

代码概念上类似：

这里的 fork 是“复制出一个独立的 Agent 执行上下文”，不是创建操作系统进程。

它的触发方式

executeSkill fork 只能由 Skill 触发。

例如：

它通常依赖 Skill 的配置：

context: fork
allowed-tools: read_file, grep_search

因此它是“技能专属的子 Agent”。

子 Agent 架构是什么

子 Agent 架构是更通用的设计：

它不要求先定义 Skill，模型可以根据任务自主派发子 Agent：

{
“type”: “explore”,
“prompt”: “找出项目里所有 checkPermission 的调用位置”
}

这里我们实现的三种角色是：

类型 能力
explore 只读探索
plan 只读规划
general 一般任务执行

核心区别

对比项 executeSkill fork 子 Agent 架构
定位 技能执行机制 通用 Agent 派发机制
触发者 Skill 配置触发 模型通过 agent 工具触发
任务来源 Skill 正文 agent 工具的 prompt
角色数量 通常由 Skill 决定 explore / plan / general
工具权限 Skill 的 allowed-tools 角色对应的工具白名单
是否能递归派发 取决于工具表 general 明确移除 agent 防递归
典型用途 执行固定工作流 探索、规划、拆分复杂任务

context 注入怎么解决

agent-tool.mjs 只负责定义工具和调用执行器：

它不需要知道：

  • Agent 类在哪里；
  • 子 Agent 如何创建；
  • 权限如何继承；
  • MCP 是否应该连接。

这些由 agent.mjs 负责：

执行工具时，主 Agent 把方法放进上下文：

于是调用关系变成：

agent-tool.mjs 依赖的是一个函数接口，而不是直接依赖 Agent 类，因此不再形成循环。

和 skill-tool 是同一种模式

当前技能工具也是这样：

工具模块只负责：

接收参数 → 调用 context 中的执行器

Agent 类负责：

真正创建子 Agent、执行技能、检查权限、处理结果

这种设计叫什么

这属于：

  • 依赖注入；
  • 控制反转；
  • 依赖倒置。

简单理解就是：

工具模块定义“我要调用什么能力”
Agent 模块决定“这个能力具体怎么实现”

这样做的主要好处是：

  1. 避免 agent.mjs 和工具模块循环 import。
  2. 工具模块更容易单独测试。
  3. 可以替换不同的执行器。
  4. 权限、上下文、项目根目录等运行时信息可以按调用传入。
  5. agent-tool.mjs 不会绕过 Agent 的统一权限和生命周期管理。

子agent的权限继承

这样主 Agent 和子 Agent 的权限模式一致：

但要注意：

  • 工具白名单限制“它能看到什么工具”；
  • checkPermission 限制“它实际能不能执行”。

两者是两层防护(体现纵深防御)：

工具白名单：能力隔离
权限检查：执行闸门

权限洗白攻击(安全向实验)

假设：主 Agent 被注入污染后，可能把危险任务”洗”给子 Agent——攻击者不需要子 Agent 有写权限，只需要主 Agent 把敏感数据带进带出。
